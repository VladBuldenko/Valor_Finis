# CLAUDE.md — Valor Finis

## Project

Valor Finis is a production-minded personal-finance application for expenses, categories, budgets, goals, analytics, and receipt/OCR workflows.

Priority:

1. business logic
2. technical correctness
3. tests/E2E
4. UX
5. visual design

Mobile is the primary client; web comes later. FastAPI is the source of truth for authorization, ownership, financial rules, analytics, and categorization. Build a scalable MVP and preserve the modular-monolith architecture unless a concrete requirement justifies more complexity.

## Architecture

Backend:

```text
Router -> Service -> Repository -> SQLAlchemy -> PostgreSQL
```

- Router: HTTP/dependencies/status/response wiring.
- Service: business rules and cross-module validation.
- Repository: SQLAlchemy queries/persistence.
- Pydantic schemas: API contracts.
- SQLAlchemy models: persistence shape.
- Domain exceptions map to HTTP centrally in `app/core/exception_handlers.py`.

Mobile:

```text
Expo route/screen -> feature service -> src/api/api-client.ts -> FastAPI
```

- Keep routes thin.
- Auth Context owns auth/session only.
- TanStack Query owns server state; component state owns form/UI state.
- Supabase mobile usage is Auth-only; finance CRUD goes through FastAPI.
- Financial/business rules stay on the backend.
- Keep TypeScript API types aligned with backend responses.
- Before non-trivial mobile implementation, read `apps/mobile/AGENTS.md` and follow the Expo-version guidance defined there.

## Critical Invariants

- Never use `float` for financial business calculations.
- Backend money uses `Decimal` + PostgreSQL `NUMERIC`.
- Preserve decimal precision across API/client boundaries.
- `user_id` comes from authenticated identity, never business request payloads.
- Scope every user-owned read/update/delete by authenticated `user_id`.
- Never expose secrets/service-role keys in client code or logs.
- Never print `.env` secret values.
- Development `X-User-Id` auth is local/test-only.
- Preserve IDs, FKs, and historical financial data when evolving the domain.
- Never weaken validation, ownership, or security merely to pass checks.

## Database / Alembic

SQLAlchemy model = desired schema. Alembic migration = path from existing schema to desired schema.

For schema changes:

1. update model;
2. create a new migration;
3. review autogenerated operations;
4. apply migration;
5. run targeted tests;
6. run full backend regression.

Rules:

- Never rewrite an already-applied migration for a new change.
- No migration for behavior-only Python/TypeScript changes.
- Prefer data/ID-preserving migrations.
- Never perform destructive production DB actions without explicit approval.
- Never perform external-network lookups from an Alembic migration unless the task explicitly approves that architecture.

## Coding Rules

General:

- Inspect existing code/patterns first.
- Do not invent files, endpoints, fields, commands, or library APIs.
- Make the smallest coherent change.
- No unrelated refactors or repository-wide formatting sweeps.
- Fix root causes; do not suppress errors.
- Prefer existing project patterns over speculative abstractions.

Python:

- Follow existing Pydantic Create / Update / Response patterns.

Comments/docs:

- Do not narrate obvious code.

## Git Safety

The LOCAL WORKING TREE is the source of truth and may be newer than `main`.

Before starting a NEW file-changing task:

1. inspect `git status --short`;
2. inspect `git diff` when relevant;
3. preserve any existing uncommitted work;
4. switch to `main`;
5. run `git pull --ff-only`;
6. confirm the working tree is clean;
7. create exactly one dedicated branch for the task BEFORE editing.

Never implement directly on `main`.

One task = one branch.

A dependent next task must start only after the previous task has been merged into `main`.

Then:

```bash
git switch main
git pull --ff-only
git switch -c <new-task-branch>
```

Never create a dependent task branch from another unmerged feature branch unless the user explicitly requests stacked branches.

Preserve uncommitted user work.

Never use:

- `git reset --hard`
- destructive `git clean`
- force push
- rebase
- stash
- restore/discard of user work
- branch deletion containing unmerged work

unless explicitly requested.

Never use:

- `git add .`
- `git add -A`

Stage intended paths explicitly.

### Local commits

Claude MAY create normal LOCAL commits autonomously while completing an approved implementation task.

Use local commits as meaningful checkpoints.

Multiple logical commits inside one task branch are allowed and preferred when the task has clearly separable completed pieces.

Examples:

- schema/migration foundation
- repository/service implementation
- API wiring
- tests
- documentation

Do not create meaningless commits after every file edit.

Commit format:

`<type>(scope): [VF-XXX] description`

Local commit != remote publication.

### Remote Git actions

Do NOT perform automatically:

- `git push`
- force push
- create or modify remote PRs
- merge PRs
- delete remote branches

unless the user explicitly authorizes the remote action.

A task can be fully completed locally, tested, reviewed, committed, and left ready for later publication.

When implementation is complete but remote publication has not been approved, finish with:

`READY TO PUSH`

The user performs the final merge.

## Quality Bar

1. inspect relevant code and current diff;
2. plan first for architecture, DB/auth/security, or meaningful multi-file work;
3. implement only agreed scope;
4. run narrow verification first;
5. fix root causes;
6. run full backend regression when backend behavior may be affected;

## Agent Workflow

- Use targeted search before opening many files.
- Use Plan mode for architecture, DB/auth/security, or meaningful multi-file work.
- Skip Plan mode for trivial fixes.
- Use subagents for isolated investigation or independent verification, not small tasks.
- Prefer fresh-context review for meaningful/high-risk diffs.

## Autonomous Local Task Execution

When the user gives an approved implementation task, treat the entire requested task as one continuous unit of work.

Default behavior:

```text
IMPLEMENT -> VERIFY -> FIX -> CONTINUE -> COMPLETE
```

Do not stop after an intermediate implementation step merely to ask whether to continue.

Continue autonomously through all normal local phases until the complete task has been implemented, verified, reviewed, and saved in local Git history.

### Required task flow

For every approved file-changing implementation task:

1. inspect relevant repository instructions and current code;
2. inspect Git state;
3. update `main` safely;
4. create the dedicated task branch;
5. inspect only task-relevant files;
6. plan when required by architecture/risk;
7. implement the complete requested scope;
8. run focused verification;
9. diagnose and fix failures caused by the change;
10. continue automatically to the next required subtask;
11. run required regression tests;
12. review `git diff`;
13. run `git diff --check`;
14. verify no unrelated changes;
15. create logical local commits;
16. verify the final branch state;
17. report the completed result.

Do not return control to the user merely because one phase is complete.

For example, if the requested task requires:

- model
- migration
- repository
- service
- schemas
- tests
- documentation

then completing the model is NOT completion of the task.

Continue automatically through migration, repository, service, schemas, tests, documentation, regression verification, diff review, and local commits.

### Self-correction

Ordinary implementation failures are not reasons to stop.

If a test, typecheck, lint check, migration check, or import check fails because of the current implementation:

1. investigate the root cause;
2. fix it;
3. rerun the narrow verification;
4. continue with the remaining task.

Do not ask the user for permission to fix ordinary defects inside the approved scope.

Never weaken valid tests, ownership rules, validation, financial correctness, or security merely to make checks pass.

### When to stop early

Stop and ask/report only when there is a genuine decision or blocker that cannot be safely resolved from:

- the user's specification;
- current repository behavior;
- established project architecture;
- existing domain conventions.

Examples:

- conflicting product requirements;
- destructive data migration with no approved policy;
- security/auth semantics that require a product decision;
- irreversible operation;
- required external credential unavailable;
- scope expansion beyond the approved task.

Do NOT stop for normal implementation details that can be resolved from the repository.

### Completion definition

Do not describe a task as complete until:

- all requested requirements were addressed;
- focused verification passes;
- required regression verification passes;
- migrations are verified when applicable;
- the final diff was reviewed;
- unrelated changes are absent;
- intended work is stored in local commits;
- final working-tree state is understood.

If remote Git actions were not authorized, complete everything locally and report:

`READY TO PUSH`
