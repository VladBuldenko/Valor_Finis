## 1. How to use this template

1. Do not edit this file to record results. Copy it to `docs/mvp/qa-evidence/<run-id>/acceptance.md` (layout in the
   evidence document) and fill the copy. This file stays the blank, all-`NOT RUN` reference.
2. One row = one journey on one platform. There are exactly 40 rows: J01–J20 on iOS and J01–J20 on Android. A journey whose
   feature is not ready stays in the table as `BLOCKED` with a blocker; it is never deleted.
3. The validator `tools/qa/validate-qa-evidence.mjs` checks this file and every run copy (see the evidence document, section 9).

## 2. Status values and what each requires

| Status | Meaning | Required before the row may carry it |
|---|---|---|
| `NOT RUN` | Not executed | Result fields stay `—` |
| `PASS` | Every expected API and UI outcome and every financial invariant observed | Device model and OS, App build identifier containing the full 40-character commit SHA, a Staging environment identifier that is `ACTIVE` in the staging register, Actual result, Evidence location (an existing file), Tester, ISO Execution date, Defect reference `none` or only Sev-3/Sev-4 defects |
| `FAIL` | At least one expected outcome or invariant not met | Same fields as `PASS`, plus a Defect reference |
| `BLOCKED` | Cannot be executed; the reason is not a product defect found by the test | Actual result stating the reason and a Blocker reference |
| `WAIVED` | **Only J18**, only under BR-5 and GAP-20, only with an owner-signed entry in the waiver register | Waiver reference that exists in [qa-evidence/waivers.md](qa-evidence/waivers.md) with status `SIGNED` |

Rules that are never relaxed:
- No automatic waiver exists. Any `WAIVED` row on a journey other than J18, or without a signed register entry, fails validation.
- A waiver removes only the waived element of the journey's checklist (BR-5); it does not make the journey `PASS`.
- A `PASS` without an existing evidence file fails validation.
- A row never receives `PASS` from a simulator, an emulator, an Expo export or a Node test. Those are not device acceptance.
- Zero open Sev-1 or Sev-2 defects is a BR-5 condition checked by the release reviewer from the run's defect register.

## 3. Common preconditions (referenced as CP-1 to CP-5)

- **CP-1** A run record exists under `docs/mvp/qa-evidence/<run-id>/` and the run ID is written on every row of the run.
- **CP-2** The build was proven to target only the designated staging environment before the run started (staging fingerprint check, evidence document section 3). No physical device test may target production.
- **CP-3** Test users are seeded staging users (QA-A, and QA-B where a row says so). All data is synthetic. No real customer data, no real receipts.
- **CP-4** Device model, exact OS version and the build's commit SHA are written into the row before the first action.
- **CP-5** Wi-Fi, no screen reader and the default text size unless the row or an SP procedure says otherwise.

## 4. Row field reference

Each row is a block with these fields, in this order: Row ID, Journey, Platform, Title, Preconditions, Test actions,
Expected API outcome, Expected UI outcome, Financial invariants, Device model and OS, App build identifier, Staging
environment identifier, Actual result, Evidence location, Defect reference, Blocker reference, Tester, Execution date,
Status, Waiver reference. The validator fails a row with a missing or renamed field.

Expected API outcomes describe what the **app** sends and receives. HTTP-level and database assertions are separate: they
are recorded only when authorized and evidenced (see the procedures document, section 1), never inferred from the UI.
